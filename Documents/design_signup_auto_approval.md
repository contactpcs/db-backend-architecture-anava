# Automatic approval of self-registered patients

Status: **built** (backend and the receptionist queue). Not yet applied to RDS or deployed.
Schema: `SQL/v1/104_normalize_email.sql`, `SQL/v1/105_signup_auto_approval.sql` (alembic 0058).
Code: `backend/app/modules/auth/signup_security.py`, `backend/app/modules/patients/registration_risk.py`.
Decisions taken with the product owner on 2026-10-04.

## What it does

A patient who signs up on their own is approved by the system when they finish
the registration wizard, if every check passes. If any check fails, the
registration waits in the receptionist's queue exactly as today, with the
reasons attached. The system never rejects anyone on its own.

Staff are not affected. A patient registered by a receptionist, clinical
assistant, doctor or admin goes through the staff endpoints, which have none of
these limits or checks. This is why no clinic Wi-Fi exemption is needed.

## Stage 1: at signup (anonymous requests)

Applies to the public patient signup endpoints only, including the older ones
the Android app still calls (`signup/verify`, `signup/complete`).

| Check | Rule | Result when it fails |
|---|---|---|
| Edge protection | AWS WAF rules (already attached). No Bot Control, no Turnstile | Blocked by AWS |
| Signup starts per IP | 15 per hour | HTTP 429 |
| Start or resend per email/phone | 10 per hour | HTTP 429 |
| OTP attempts per IP | 10 per hour, on top of Cognito's own limits | HTTP 429 |
| Email format and length | As today | HTTP 422 |
| Disposable email | Domain is on the list of throwaway providers kept in the repo | Refused |
| Email can receive mail | The domain exists and has a mail server. If the lookup times out or no DNS server answers, the signup is allowed | Refused |
| Same mailbox already registered | Compared after normalization (below) | Refused, as today |
| Phone | Converted to E.164. Country code must be in the allowed list (`+91` today) | Refused |
| Password, OTP ownership | Cognito, as today | As today |

**Email normalization.** Lower-cased and trimmed always. Gmail: dots ignored,
`+tag` dropped, `googlemail.com` treated as `gmail.com`. Outlook, Hotmail, Live,
iCloud, Me, Proton and Fastmail: `+tag` dropped. Any other domain is left as
typed, because there a `+tag` address can be a different person.

Stored at signup: the patient's IP (`patients.signup_ip`). The signup time is
the existing `patients.created_at`.

## Stage 2: during the wizard

No change. The patient stays inactive and can reach only the registration
pages (existing middleware allowlist).

## Stage 3: when registration completes

| Flag code | Rule |
|---|---|
| `duplicate_patient` | Another patient at the same clinic has the same first name, last name and date of birth |
| `ip_velocity` | More than 24 completed self-registrations from the same IP in 24 hours |
| `suspicious_name` | Name contains a digit, three or more of the same letter in a row, a test word (`test`, `asdf`, `qwerty`, `abc`, `xyz`, `dummy`, `fake`), or the first name is a single letter |
| `implausible_dob` | Date of birth is in the future, or the age is over 150 years |
| `completed_too_fast` | Wizard finished less than 30 seconds after signup |

A single-letter **last** name is not flagged: an initial as a surname is common
in South India.

Outcome:

| Result | What is written |
|---|---|
| No flags, feature on | `approval_status = 'approved'`, `approval_method = 'auto'`, `approved_by` empty, `approved_at` set, `risk_flags = []`, profile activated. The API shows the approver as "System" |
| Any flag, or feature off | `approval_status` stays `pending`, `risk_flags` holds the codes, receptionists are notified as today |
| Receptionist approves later | `approval_method = 'manual'`, `approved_by` = that receptionist |

The checks run and `risk_flags` is stored even when the feature is off, so the
flags can be watched for a while before automatic approval is switched on.

## Settings

All are environment settings, changeable without new code.

| Setting | Default |
|---|---|
| `AUTO_APPROVE_SELF_REGISTRATION` | `false` (fully manual until switched on) |
| `SIGNUP_START_LIMIT_PER_IP_PER_HOUR` | 15 |
| `SIGNUP_CONTACT_LIMIT_PER_HOUR` | 10 |
| `SIGNUP_OTP_LIMIT_PER_IP_PER_HOUR` | 10 |
| `SIGNUP_IP_VELOCITY_LIMIT_PER_DAY` | 24 |
| `SIGNUP_MIN_WIZARD_SECONDS` | 30 |
| `SIGNUP_MAX_AGE_YEARS` | 150 |
| `SIGNUP_ALLOWED_PHONE_COUNTRY_CODES` | `["+91"]` |

| `TRUST_FORWARDED_FOR` | `false` (see "Client IP") |

## Schema

**`ops.normalize_email(email)`** — the one definition of "the same mailbox".

**`core.profiles.email_normalized`** — generated by Postgres from `email` on
every insert and update, so it cannot drift whichever code path changes an
email. Indexed, not unique: older accounts may already share a mailbox.

**`core.patients`** gains:

| Column | Type | Meaning |
|---|---|---|
| `approval_method` | `TEXT`, `'auto'` or `'manual'` | Who approved: the checks, or a staff member. Empty until approved |
| `risk_flags` | `JSONB`, default `[]` | Flag codes this registration raised |
| `signup_ip` | `INET` | Where the self-signup came from. Empty for staff-registered patients |

Existing approved patients are marked `approval_method = 'manual'`.

**`ops.signup_security_log`** — one row per decision. It is both the counter
the rate limits read and the audit trail.

| Column | Meaning |
|---|---|
| `checkpoint` | `signup_start`, `signup_resend`, `otp_confirm`, `registration_complete` |
| `outcome` | `allowed`, `blocked`, `flagged`, `auto_approved` |
| `reason` | Which rule blocked or flagged it |
| `ip` | Caller's IP |
| `contact_hash` | Keyed one-way hash of the normalized email or phone. The raw value is never stored |
| `patient_id` | Set on `registration_complete` rows |
| `created_at` | When |

Append-only: the app login can insert and read, not update or delete. RLS is
forced, role `system` only, like the other tables written before a user
identity exists.

A rate limit counts the `allowed` rows for that IP or contact in the last
hour. A blocked attempt is logged but does not extend the block.

## How a decision can be traced

- Per patient: `approval_status`, `approval_method`, `approved_by`,
  `risk_flags`, `signup_ip` on the patient row.
- Per event: `ops.signup_security_log` rows for that patient or IP.
- The existing `patient_registration_decided` event carries the method
  (`auto` or `manual`), so it also lands in `activity_logs`.

## Client IP

Behind the load balancer the app currently sees the load balancer's address
for every request. With `TRUST_FORWARDED_FOR=true` it takes the last address
in `X-Forwarded-For`, which is the one the load balancer itself added and a
client cannot forge.

This is only safe if the API tasks accept traffic from the load balancer
alone. **To confirm in AWS before switching it on:** the ECS tasks have no
public IP, and their security group allows port 8000 only from the load
balancer's security group.

Until it is on, the app protects itself: an address that is not a public
internet address (the load balancer's own, or localhost) is treated as
"caller unknown". No per-IP limit is applied to it, `ip_velocity` cannot
fire, and no `signup_ip` is stored. The per-contact limit and every other
check still work. So deploying with the setting off cannot lock patients
out; it only means the IP rules are not yet in force.

## Known limits

- Two requests arriving in the same instant can both pass a limit that had one
  slot left. The WAF handles floods; these limits handle slow abuse.
- `signup_security_log` is not purged. It grows by a few rows per signup.
- If the provider list in `ops.normalize_email` changes, `email_normalized`
  must be rebuilt (drop and re-add the column).

## Deploy order

1. Apply alembic 0058 (safe under the current backend).
2. Add `SIGNUP_HASH_SECRET` to the task secrets.
3. Deploy the backend with `AUTO_APPROVE_SELF_REGISTRATION=false`.
4. Confirm the client-IP precondition, then set `TRUST_FORWARDED_FOR=true`.
5. Watch `risk_flags` on new registrations, then set
   `AUTO_APPROVE_SELF_REGISTRATION=true`.
6. Switch the WAF rules from Count to Block.

## Not included

- Automatic rejection.

  after completion and sends an active patient to the dashboard.
